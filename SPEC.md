# lgtm-quiz — spec

A personal tool that makes a developer prove they understand code (especially AI-generated code)
before they commit it. It also teaches: what the dev doesn't know, it explains and re-checks.

Status: design agreed in conversation, only `src/spike.ts` exists.

## 1. Principles

- **Personal, not team.** No CI check, no shared config, no enforcement against the dev. A dev may opt out of the tool entirely.
- **Language-agnostic.** Levels describe the *kind* of question, not a language. The LLM generates questions from the diff.
- **Backend-agnostic.** Uses whichever local AI the dev already has.
- **Leaves no trace in the repo.** Local ignore via `.git/info/exclude`.
- **Teaches, not only blocks.** "I don't know" starts a teaching flow, never a plain failure.

## 2. Main flow

The primary trigger is a command the dev runs when they consider the work ready:

```
lgtm-quiz start        # analyze staged diff (or working tree), open the quiz in the browser
```

1. Read the diff (staged by default).
2. Rank hunks by risk; drop hunks with no behavior change (log removals, version bumps, formatting).
3. Generate questions for the enabled levels, weighted by the knowledge profile.
4. Validator pass removes ambiguous or guessable questions.
5. Open the local web app, dev answers, tool grades, teaches on IDK, records results in the profile.
6. Exit code 0 on pass, non-zero otherwise (so it can also be used from a hook).

Optional, off by default: `lgtm-quiz hook on` installs a pre-commit hook that runs `lgtm-quiz start`
and blocks the commit until it passes. `lgtm-quiz hook off` removes it.

## 3. Question levels (each independently toggled, personal setting)

| Level | Asks about | Example |
| --- | --- | --- |
| 1. Mechanics | What a construct does in this exact spot | "What does this `.map` return here?" / "Why a Promise here?" |
| 2. Decisions | Why this choice | "Why a new service instead of extending the existing one?" |
| 3. Architecture | Bigger structure, tradeoffs, impact | "What else breaks if this state moves to the shared store?" |

Level 1 uses both multiple choice and written answers (default mix ~70/30, a personal setting).

## 4. Question model

```
id, level (1|2|3), type ('choice'|'written'), concepts[] (normalized tags)
anchor: file + line range (the UI highlights it)
scenario: concrete input/state (required; no vague "what happens?")
prompt
choice:  options[], correct
written: rubric { mustInclude[], misconceptions[] }
teaching: generated ON DEMAND when IDK is pressed
```

Quality rules enforced in code:

- Shuffle option order; reject questions whose correct option is much longer than the rest (known LLM tell).
- Reject questions without a scenario.
- Reject questions answerable without the diff (validator pass tries to answer blind).
- If a diff has only N meaningful hunks, ask N questions, never pad.

## 5. Grading

- Choice: exact match, no LLM.
- Written: separate LLM call sees question + rubric + answer (not the diff). Outcomes: correct / partial / wrong.
  Partial shows the missing points and counts as half in the profile.
- "Grade seems wrong" button records a dispute locally, to improve the grader prompt.
- Small local models grade written answers less reliably; warn, or lean on multiple choice.

## 6. "I don't know" flow

1. Dev presses IDK.
2. Tool generates (now, on demand) a short explanation of the concept, applied to their code.
3. A follow-up question on the same concept with a different scenario.
4. Correct follow-up → original marked **learned**. Wrong → explain again, repeat.

Rules: IDK never passes by itself; the concept is marked unknown in the profile and comes back via spaced
repetition; a cap on IDKs per quiz; no penalty for honesty.

## 7. Knowledge profile (local)

Per concept: `{ correct, wrong, idk, lastSeen, confidence }`, with decay over time.
Selector weighs hunk risk × uncertainty about the dev on that hunk's concepts.
Concept questions fade as mastery grows; change-specific questions (about this exact diff) never do.
Random sampling even on mastered concepts, so the profile can't be gamed once and forgotten.
Stored per user under `~/.config/lgtm-quiz/`, never shared.

## 8. Making the AI use it

The AI can't be trusted to remember instructions, so layers from most to least reliable:

1. Optional git pre-commit hook (deterministic; works whichever tool wrote the code).
2. Claude Code `PreToolUse` hook on `git commit` (deterministic inside that tool).
3. Instruction files generated by `init`, saying: *don't commit; when work is complete tell the developer to
   run `lgtm-quiz start`; if a commit is blocked by the quiz, stop and report it.*
   Targets: `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/lgtm-quiz.mdc`, `GEMINI.md`, `.github/copilot-instructions.md`.
4. Optional MCP server with a `request_review` tool, so agents have a standard way to ask for the quiz.

In a non-interactive (agent) session the command exits with a clear message ("quiz pending, ask the developer
to run `lgtm-quiz start`") instead of opening a window and waiting.

Start with Claude Code + plain git; add other agents later.

## 9. Install per repo

```
npx lgtm-quiz init
```

- Finds the repo root.
- Adds ignore entries to `.git/info/exclude` by default (never touches tracked files). `--gitignore` writes
  `.gitignore` instead.
- Entries: `.lgtm-quiz/` and any instruction-file snippets.
- Writes the agent instruction snippets.
- Idempotent. `lgtm-quiz uninstall` reverts everything it added.
- Hook install is separate and opt-in (`lgtm-quiz hook on`):
  - Husky repo: create `.husky/pre-commit` (Husky runs it) and exclude it locally. Never overwrite an existing one.
  - No Husky: write `.git/hooks/pre-commit`, chaining to any existing hook.
  - Note: Husky sets `core.hooksPath` locally, which overrides any global hook, so the hook is per repo.

## 10. LLM backends (adapter interface)

`claude -p` (first), `codex exec`, `gemini -p`, Ollama / OpenAI-compatible endpoint, raw API key.
Chosen in the personal config. Prompts, schema and UI are identical across backends.

## 11. UI (local web app)

- CLI starts a server on `127.0.0.1` with a random port and a one-time token in the URL, opens the browser
  (`xdg-open` / `open` / `start`), shuts down when the session ends. Terminal quiz fallback when no display.
- Code (highlighted anchor) on one side, question on the other; IDK button; result and explanations.
- Grading happens on the server; the answer key is never sent to the page.
- Settings page (levels, mix, backend) and profile view (concepts known / failing).
- Stack: static frontend (Svelte or React + Vite) with Shiki for code, tiny Node server with two endpoints
  (`GET /session`, `POST /answers`), bundled inside the npm package.

## 12. Build order (each step done only when its check passes)

1. **Spike** (exists): questions from a real diff. Check: most questions judged good on 20-30 diffs.
   Known issues from the first run: correct option is always the longest; pure log-removal hunks produce
   trivial questions; some questions are general knowledge.
2. **Question schema + validator + eval harness.** Check: change a prompt, see quality go up or down.
3. **Diff + risk modules.** Check: ranking matches a human's on the saved diffs.
4. **Web quiz** with choice + written + IDK flow. Check: full session runs and grades.
5. **Profile + selector.** Check: simulated devs of known skill; selector stops asking what they know.
6. **`init` / `hook on|off` / `uninstall`.** Check: `git status` stays clean after init.
7. **Instruction files, backends, packaging.**

## 12b. Later features

**Explain-it questions.** A third question type: "In your own words, what does this function / method / class do?"
- Written answer; anchor points at the function, method or class; the prompt is fixed.
- The generator writes a rubric from the code first (main behaviors, inputs/outputs, side effects, edge cases);
  the grader checks the answer against it with the usual correct / partial / wrong outcomes.
- Grade meaning, not terminology: a plain-words explanation from a beginner can be fully correct.
- Works at every level (small function, service purpose, whole module). IDK flow: explain, then ask the dev to
  explain it back.

**Voice input (final stage).** The dev speaks the explanation; the transcript goes into the same written-answer
grader, so voice adds an input method only. Options: browser Web Speech API (no setup, but often cloud-based and
uneven across browsers) or local speech-to-text such as whisper.cpp (private and offline, but a bigger install).
Leaning local, to match the local-AI principle.

## 13. Decisions

- Name: **lgtm-quiz**.
- Pass rule: at least **70%** correct, configurable in the personal config.
- Explanations are shown **after each answer**.
- Retries always generate **fresh** questions.

## 14. Prior art (checked 2026-10-28, via web search only, not verified in depth)

Similar tools exist, so this is not a new idea. Mostly git hooks, GitHub Actions and agent skills:
Sphinx (git hook), bel-ai-jar (Python pre-commit hook), Commit Comprehension Gate and PR Guard (GitHub Actions),
quiz-gate and merge-readiness (Claude Code skills), GitHuman (staging review, no quiz).
What lgtm-quiz adds: local browser UI, three question levels, the IDK teaching flow, and a personal
adaptive knowledge profile. Review these projects before building, to learn from them.
